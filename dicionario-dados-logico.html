Escopo e validação: este documento descreve o modelo lógico proposto e o script SQL disponibilizado. A implementação ainda precisa ser executada em um servidor MySQL 8.0.16 ou superior. Dados da massa são fictícios; bairros, taxas e estoques mínimos ilustrativos devem ser confirmados com a organização.

1. Convenções e arquitetura

  • SGBD: MySQL 8.0.16 ou superior. Engine InnoDB; checks precisam ser efetivamente aplicados nesta versão.
  • Codificação: utf8mb4; collation do schema utf8mb4_0900_ai_ci.
  • Nomes: tabelas em maiúsculas no modelo; colunas em snake_case minúsculo no SQL.
  • PK: coluna identificadora com prefixo id_; PKs simples usam BIGINT UNSIGNED AUTO_INCREMENT. Tabelas associativas usam PK composta quando indicado.
  • FK: referencia a PK da tabela de origem e usa tipo compatível; índices são declarados para apoiar junções e filtros.
  • Monetário: DECIMAL(10,2); não usar ponto flutuante para valores financeiros.
  • Quantidade de ingredientes: DECIMAL(12,3); quantidade unitária de produto em pedido: INT UNSIGNED.
  • Data/hora: DATETIME, data e hora local; o MySQL não oferece TIMESTAMP WITH TIME ZONE.
  • Indicadores: TINYINT(1) com 0 = não/inativo e 1 = sim/ativo.
  • Documento relacionado: modelo lógico relacional completo e script SQL.

2. Dicionário físico das tabelas

As descrições e restrições resumem o modelo lógico. PK indica chave primária; FK indica chave estrangeira; NOT NULL exige valor; UNIQUE impede duplicidade; CHECK valida domínio/limite; DEFAULT define valor inicial.

7. Registro de acesso (proposta)

O SQL atual inclui HISTORICO_STATUS_PEDIDO, que registra alterações do pedido; isso não substitui um log geral de acesso ao sistema. Recomenda-se criar, em etapa futura, uma estrutura separada como LOG_ACESSO com: identificador, usuário da aplicação, ação (LOGIN, LOGOUT, SELECT, INSERT, UPDATE ou DELETE), recurso, registro afetado, data/hora, resultado e IP de origem. Não registrar senhas, tokens ou dados sensíveis desnecessários. Esta tabela não integra as 20 tabelas entregues no script.

8. Privacidade e LGPD

  • Usar telefone e endereço do cliente somente para atender o pedido, processar pagamento e executar a entrega, com transparência sobre a finalidade.
  • Limitar a visualização desses dados aos papéis que precisam deles para o trabalho.
  • Não usar dados reais na massa de demonstração. A massa do script é integralmente fictícia.
  • Estabelecer prazo de retenção e descarte/anonimização com o responsável pela operação e orientação adequada.
  • Não armazenar número completo de cartão nem código de segurança; o modelo registra apenas forma e valor do pagamento.
  • Proteger credenciais e manter auditoria das operações administrativas.

A definição de base legal, prazo de retenção e responsabilidades do controlador/operador deve ser validada pela organização; este documento não substitui avaliação jurídica.
